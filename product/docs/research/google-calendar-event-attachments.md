# Research: Google Calendar event attachments — alternatives to "store separately + link in notes"

_Researched: 2026-09-14._

## Summary

Google Calendar has a **native attachment model**, but it is strictly a *reference* model: an event's `attachments[]` entries point to **Google Drive files** (URL + title + MIME type), and there is no API that stores arbitrary binary content on the event itself. The practical alternative to "app-owned storage + link in the notes" is therefore: **the user attaches the file in the Google Calendar UI** — current Google Calendar Help allows picking a Drive file *or uploading from the computer* (the upload lands in Drive), with no Workspace-only restriction documented — and planner2 then reads the native `attachments[]` metadata with the existing `calendar.readonly` scope and opens the file via its Drive link. Having the *app* upload the file to Drive and attach it via `events.patch` also works technically (any MIME type, max 25 attachments per event), but it modifies the event through the API, which conflicts with the "events are created and modified in Google Calendar only" constraint. `extendedProperties` can carry machine-readable pointers but are hidden strings, and the iCalendar `ATTACH` property (RFC 5545) has no documented support in Google's import paths.

## Findings

1. **Native attachment model exists, and it is Drive-references only.** The Event resource has an `attachments[]` list with `fileUrl`, `title`, `mimeType`, `iconLink`, and `fileId`. `fileId` is read-only and "for Google Drive files, this is the ID of the corresponding `Files` resource entry in the Drive API"; `fileUrl` is "required when adding an attachment" and "for adding Google Drive file attachments use the same format as in `alternateLink` property of the `Files` resource in the Drive API". The only writable attachment field is `fileUrl` (`iconLink` "can only be modified for custom third-party attachments"). There is no field that accepts file content. [Events resource reference](https://developers.google.com/workspace/calendar/api/v3/reference/events)

2. **Modifying attachments requires `supportsAttachments=true`; max 25 per event.** The reference states: "In order to modify attachments the `supportsAttachments` request parameter should be set to `true`. There can be at most 25 attachments per event." The `supportsAttachments` query parameter ("Whether API client performing operation supports event attachments. Optional. The default is False.") exists on `events.insert`, `events.update`, `events.patch`, and `events.import`. [Events resource reference](https://developers.google.com/workspace/calendar/api/v3/reference/events) [Events: import](https://developers.google.com/workspace/calendar/api/v3/reference/events/import)

3. **Official how-to is explicitly "Add Drive attachments to events".** The Create events guide says you can attach "Google Drive files such as meeting notes in Docs, budgets in Sheets, presentations in Slides, or any other relevant Google Drive files", at `events.insert` time or later via `events.patch`, and describes exactly two parts: (1) get the file's `alternateLink` URL, `title`, and `mimeType` from the Drive API Files resource (typically `files.get`); (2) create or update the event with the `attachments` fields set and `supportsAttachments=true`. The generated client-library schema states it flatly: "Currently only Google Drive attachments are supported." [Create events guide](https://developers.google.com/workspace/calendar/api/guides/create-events) [Schema$Event (generated from the API discovery doc)](https://googleapis.dev/nodejs/googleapis/latest/calendar/interfaces/Schema$Event.html)

4. **In the Google Calendar UI, users can attach Drive files OR upload from their computer — no Workspace-only restriction is documented.** Google Calendar Help ("Add attachments to your events") says: "You can add files from Google Drive or upload files from your computer," via the "Add a Google Drive attachment" button in the description box; choosing **Upload** stores the file in Google Drive ("Attachments are stored in Google Drive"). The page lists no account-type requirement; the only documented blocker is an admin disabling Drive for a work/school organization ("Attachments can't be added because Google Drive is disabled by your domain administrator") and the need to be signed in with the account linked to Drive. So free personal Google accounts can use this path. [Google Calendar Help: Add attachments to your events](https://support.google.com/calendar/answer/6192039?co=GENIE.Platform%3DDesktop&hl=en)

5. **Guests do not automatically get access; sharing is a separate step.** The same Help page: "Attachments are stored in Google Drive, so your guests don't automatically have permission to view your attachments." On save, the UI offers three options — "Anyone with the link can view, comment, or edit", "Guests of this event can view, comment, or edit" (requires guests to have a Google Account), or "Save without sharing" (guests see only the file title). Also: "The names of any files you attach to your event will be visible to both invited guests and anyone with access to the event details." [Google Calendar Help: Add attachments to your events](https://support.google.com/calendar/answer/6192039?co=GENIE.Platform%3DDesktop&hl=en)

6. **No API accepts binary blobs on the event itself.** Confirmed from the resource representation: `attachments[]` subfields are `fileUrl` (writable, a URL), `title`, `mimeType`, `iconLink`, and read-only `fileId` — all strings/metadata. There is no content/data field anywhere on the Event resource. Attaching arbitrary bytes therefore always goes through Drive. [Events resource reference](https://developers.google.com/workspace/calendar/api/v3/reference/events)

7. **The Drive-backed path accepts arbitrary file types.** Drive API `files.create` "supports an /upload URI and accepts uploaded media with … Accepted Media MIME types: `*/*` (any valid MIME type)", with simple (≤5 MB), multipart, and resumable upload types. So photos of tickets, PDFs, and docs can all be uploaded to Drive and then referenced from an event per finding 3. Limits to note: 25 attachments per event (finding 2), and attendee visibility is governed entirely by Drive sharing (finding 5). [Drive API: files.create](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/create) [Drive API: Upload file data](https://developers.google.com/workspace/drive/api/guides/manage-uploads)

8. **`extendedProperties` are hidden string key-value pairs, not file carriers.** The Extended properties guide describes them as "hidden key-value pairs" that let an app "store application-specific data for an event without having to utilize an external database." Values are strings only; limits: key ≤ 44 characters (longer keys silently dropped), value ≤ 1024 characters (silently truncated), up to 300 properties totaling ≤ 32 kB across all copies of the event. `shared` properties are visible/editable by all attendees via the API; `private` properties are per-calendar-copy. They are searchable via `events.list` with `privateExtendedProperty`/`sharedExtendedProperty`. They never appear in the Google Calendar UI. [Extended properties guide](https://developers.google.com/workspace/calendar/api/guides/extended-properties)

9. **`description`, `source`, and `gadget` are not attachment mechanisms.** The reference defines `description` as "Description of the event. Can contain HTML. Optional." — writable, with no length limit documented in the API reference; it is the natural carrier for a link (the baseline option). `source` is a `{url, title}` pair where the URL "must be HTTP or HTTPS" — a single provenance link, not a list. `gadget` is deprecated: "Gadgets are deprecated; this structure is instead only used for returning birthday calendar metadata." [Events resource reference](https://developers.google.com/workspace/calendar/api/v3/reference/events)

10. **iCalendar path: RFC 5545 ATTACH exists, Google support is undocumented.** RFC 5545 §3.8.1.1 defines the `ATTACH` property: "This property provides the capability to associate a document object with a calendar component. The default value type … is URI. The value type can also be set to BINARY to indicate inline binary encoded content." On Google's side, `events.import` takes a JSON Events resource — there is no ATTACH mapping; the only attachment input is `attachments[].fileUrl` in the Drive `alternateLink` format (with `supportsAttachments`). The consumer ICS import Help page documents importing `.ics`/`.csv` files and explicitly notes "guests and conference data for that event are not imported"; it says nothing about `ATTACH`. Whether an imported ICS `ATTACH` (URI or inline binary) survives is undocumented — do not rely on it. [RFC 5545 §3.8.1.1](https://datatracker.ietf.org/doc/html/rfc5545#section-3.8.1.1) [Events: import](https://developers.google.com/workspace/calendar/api/v3/reference/events/import) [Google Calendar Help: Import events](https://support.google.com/calendar/answer/37118?hl=en)

11. **Read path: `calendar.readonly` suffices for attachment metadata.** `calendar.readonly` means "See and download any calendar you can access using your Calendar"; `attachments[]` is part of the Event resource returned by `events.get`/`events.list` with no documented scope restriction on that field, so planner2's existing read-only scope gets back `fileId`, `fileUrl`, `title`, `mimeType`, `iconLink`. But the *bytes* live in Drive: following the link works for the signed-in user in a browser subject to Drive permissions; programmatic download via the Drive API needs a Drive scope — `drive.readonly` (restricted) or `drive.file` (per-file, covers only files the app created or the user opened with the app). [Calendar API scopes](https://developers.google.com/workspace/calendar/api/auth) [Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth) [Drive API: files.get](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/get)

12. **Write path scope requirements.** Attaching via the API is an event modification: `events.insert`/`update`/`patch`/`import` require a Calendar write scope — `calendar`, `calendar.events`, `calendar.events.owned`, or `calendar.app.created` — *plus* a Drive scope to upload the file first (`drive.file` suffices for files the app itself creates). This is materially more OAuth surface than planner2's current `calendar.readonly`, and it means the app writes to the user's calendar. [Events: import authorization](https://developers.google.com/workspace/calendar/api/v3/reference/events/import) [Calendar API scopes](https://developers.google.com/workspace/calendar/api/auth) [Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)

## Options for the scenario (arbitrary files stored *with* an event)

| Option | Avoids "store separately + link in notes"? | Respects "modified in Google Calendar only"? | Notes |
|---|---|---|---|
| (a) App-owned storage, link in `description` | No — this is the baseline | Yes (user pastes link) | `description` supports HTML; link is visible everywhere; app owns hosting/keys by event id/`iCalUID` |
| (b) User attaches Drive file in the Google Calendar UI | **Yes** — native attachment; file lives in the user's own Drive, no link-in-notes needed | **Yes** — all modification happens in Google's UI | Works for personal accounts per current Help; upload-from-computer lands in Drive; planner2 reads `attachments[]` with existing `calendar.readonly` and opens `fileUrl`; guest access governed by Drive sharing; ≤25 per event |
| (c) App uploads to Drive (`files.create`) + attaches via `events.patch` | **Yes** — native attachment, no link in notes | **No** — the app modifies the event via API; needs `calendar.events`/`calendar` + `drive.file` scopes | Only way to automate native attachments; violates the stated constraint |
| (d) `extendedProperties` pointers to app-owned storage | Partially — storage is still separate, but no visible link in notes | No — setting them requires write access | Hidden strings (≤1024 chars/value, ≤32 kB/event); app-only visibility; searchable; good as a machine-readable complement, not a user-facing answer |
| (e) App-owned storage keyed by event `id`/`iCalUID` without touching the event | No — storage separate, and no link at all | Yes | Invisible to the user in Google Calendar; pairing problem remains (recurring events share one `iCalUID`, instances have distinct `id`s) |

**Bottom line:** the only option that avoids both "app-owned storage" and "link in the notes" while keeping all event modification in Google Calendar is **(b): the user adds a native Drive attachment in the Google Calendar UI** (Drive file or computer upload), and the read-only client surfaces the native `attachments[]` entries. Option (c) achieves the same data model programmatically but breaks the modification constraint.

## Gaps

- Whether an ICS `ATTACH` property (URI or inline binary) survives Google Calendar's import UI or `events.import` is **undocumented**; would need an empirical test with a real account before relying on it either way.
- The API reference documents no length limit for `description`; observed practical limits (often cited ~8k characters) are not in primary docs — verify empirically if long descriptions matter.
- The Help page's silence on account type strongly implies personal accounts can attach files, but Google does not state it positively; a quick manual check with a free account would remove all doubt.
- `iconLink`'s mention of "custom third-party attachments" hints at a legacy non-Drive attachment type, but no current primary doc describes creating one; treat Drive as the only supported source.
